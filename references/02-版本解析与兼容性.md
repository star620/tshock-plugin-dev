# 02 版本解析与兼容性

> **核心原则**：版本更新是常态（例：Terraria 1.4.5.8 已发布、TShock 尚在跟进），任何静态版本表都会过时。**以运行时动态解析为唯一来源，静态表仅作历史参考。**

## 版本四元组

一次开发前必须确定：

```
客户端版本（Terraria）↔ 服务端版本（TShock）↔ TShock 对应 Terraria 版本 ↔ .NET TFM
```

## 解析流程（每轮开发必做，不缓存旧结论）

### 第 1 步：确认目标
- 用户已回答（Phase 0）→ 直接使用
- 用户说「最新」或答不上来 → 用在线查询的最新稳定版

### 第 2 步：在线查询 TShock 发布版本
- API：`https://api.github.com/repos/Pryaxis/TShock/releases?per_page=10`
- 从发布名解析：`TShock 6.1 for Terraria 1.4.5.6` → 版本 `6.1.0`，对应 Terraria `1.4.5.6`
- 跳过 `prerelease: true` 的预发布版本（除非用户明确要开发 beta）
- 得到：`最新 TShock 版本 = X，对应 Terraria = Y`

### 第 3 步：在线查询 NuGet 包版本
- API：`https://api.nuget.org/v3-flatcontainer/tshock/index.json`
- 返回全部版本列表（如 `6.0.0, 6.1.0`），取最高稳定版本号
- 与第 2 步交叉验证：NuGet 最高版本应等于 GitHub 最新发布版本

### 第 4 步：确定目标框架（TFM）
- 还原 NuGet 包后读取 `~/.nuget/packages/tshock/<版本>/lib/` 下的目录名（如 `net9.0`）
- **该目录名即为插件应使用的 `<TargetFramework>`**，对未来任何版本永久有效
- 无包时（门禁场景）参考下表或用户源码的 csproj

### 第 5 步：确定测试服务器
- 用户本地服务器（版本匹配）> 自动下载官方发布 zip（win-x64）
- 下载 URL 从第 2 步返回的 `assets[].browser_download_url` 中匹配 `win-x64`

## 版本门禁（硬性规则）

**目标 Terraria 版本没有对应 TShock NuGet 包时**（即 TShock 尚未跟进该版本）：

1. **必须明确告知用户**：无法为该版本编写插件（无编译引用、无官方服务器可加载验证）
2. **唯一例外**：用户明确说明本地有「已跟进该 Terraria 最新版本的 TShock 源码」→ 允许继续，但编译引用改用用户本地源码编译出的 `TShockAPI.dll`（或直接引用其 TShock 工程），若用户无可加载测试服务器，Phase 7 加载验证降级为仅编译验证
3. 官方发布 zip 降级仅适用于「TShock 已发布该版本但 NuGet 包暂缺」的过渡情形（罕见，正常情况下发布与 NuGet 同步）

**新版本风险提示**：目标为 1.4.5.7 / 1.4.5.8 等新版本时，先提示实验性风险（OTAPI / TShock 可能未完整适配，见历史参考表），再按门禁判断；用户坚持开发 → 用本地跟进源码路径，并在交付时明确标注「实验性适配」。

## 兼容性规则

| 规则 | 说明 |
|---|---|
| 客户端 = 服务端 | Terraria 1.4.5.x 客户端只能连接 1.4.5.x 服务端 |
| TFM = 服务端运行框架 | 插件 TFM 必须与服务端一致（TShock 6.x = net9.0） |
| NuGet 包版本 = TShock 版本 | csproj 中 `PackageReference Include="TShock"` 的版本等于目标 TShock 版本 |
| 插件二进制兼容 | 插件 DLL 不随服务端版本升级而自动兼容，升级 TShock 后需重新编译验证 |
