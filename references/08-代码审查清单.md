# 08 代码审查清单

Phase 5 按此清单逐项自查并修复，向用户报告审查结论（发现问题数/修复情况）。

## 一、正确性与健壮性

- [ ] 空引用防护：`TShock.Players[i]` 可能为 null；`plr.TPlayer`、`plr.Account` 访问前判空
- [ ] 真实玩家判断：事件内 `plr.RealPlayer && plr.Active` 过滤非玩家连接
- [ ] 登录判断：涉及账号数据的逻辑检查 `plr.IsLoggedIn`
- [ ] 权限检查：每个命令/敏感操作都有权限校验
- [ ] JSON 异常处理：配置/缓存读取有 try-catch，损坏时给友好错误不崩溃
- [ ] 数组/索引越界、除零、空集合遍历等边界
- [ ] 数值类型溢出（Tick 累加、秒数累计用 long 等）

## 二、线程安全

- [ ] 多线程访问共享集合：用 `ConcurrentDictionary`/锁，禁止裸 `Dictionary` 并发写
- [ ] 异步回调回到主线程操作游戏对象（`Main.QueueMainThreadAction`）
- [ ] 定时器/Task 生命周期与 Dispose 匹配，避免后台任务残留

## 三、资源与生命周期

- [ ] 事件注册/注销**成对**（Initialize 注册的全部在 Dispose 注销）
- [ ] `Dispose(bool)` 调用 `base.Dispose(disposing)`
- [ ] 文件句柄/流及时释放（`using` 或 finally）
- [ ] 配置文件修改后不重复创建

## 四、API 与版本兼容

- [ ] 所用 API 在目标 TShock 版本存在（对照 L1/L3 源码核对签名）
- [ ] 不使用已废弃 API（对照参考源确认）
- [ ] csproj 的 TFM 与 TShock 包版本 = Phase 1 解析结果
- [ ] 不依赖 TShock 内部私有成员（应使用公开 API）

## 五、代码组织与可维护性

- [ ] 每个类 ≤ 400 行、单一职责，无「上帝类」
- [ ] 中文 `//` 注释解释「为什么」，无废话注释
- [ ] 方法/类命名清晰（动词开头、职责命名）
- [ ] 无魔法数字（用常量或注释说明）
- [ ] 无复制粘贴重复代码（提取共用方法）
- [ ] 配置/缓存分离，高频数据不混入低频配置

## 六、单测覆盖

- [ ] 每个纯逻辑方法有测试
- [ ] 测试先红后绿（不是事后补写）
- [ ] 边界与错误路径已覆盖

## 七、安全

- [ ] 命令不泄露服务器敏感信息（路径、凭据）
- [ ] 聊天消息拼接防注入（玩家名/参数转义或白名单）
- [ ] 不使用明文存储敏感数据（如涉及）
- [ ] 不执行任意用户输入的命令/代码

## 审查报告格式

```
代码审查结论：
- 发现 N 个问题，已修复 N 个
- 高风险：<列表或"无">
- 遗留说明：<如有>
```
