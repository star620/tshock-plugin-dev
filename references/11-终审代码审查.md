# 11 终审代码审查（交付前末道关卡）

Phase 8 在部署验证通过后、交付前执行。对本次开发/修改的**全部代码**（含测试）做一次整体终审，重点确认四件事：**方法名是否正确、是否存在缺陷、是否有多余字段、代码整体上有没有问题**。

与 Phase 5 的区别：Phase 5 是开发中随写随查，Phase 8 是交付前把最终代码整体再过一遍，发现问题必须全部修复后才允许进入交付。

审查对象：本次新增/修改的 .cs 文件。不审查参考源码、第三方代码。

## 一、方法名审查

逐方法过一遍（类内每个 public/private 方法都检查）：

- [ ] 方法名是否为动词短语（`Get*`/`Set*`/`Add*`/`Remove*`/`Load*`/`Save*`/`Validate*`/`Parse*`/`Send*`/`On*`）
- [ ] 无拼写错误（拿不准就查词典，禁止自造拼错词）
- [ ] 语义准确：名字与实现行为一致，不误导阅读者（如返回 bool 的不要叫 `GetData`）
- [ ] 布尔方法是否用 `Is`/`Has`/`Can` 前缀（`IsValid`、`HasPermission`、`CanConnect`）
- [ ] 异步方法是否以 `Async` 结尾（`LoadNodesAsync`）
- [ ] 事件处理方法是否用 `On*` 命名，且不与普通业务方法混淆
- [ ] 私有辅助方法命名风格与类内其他方法一致（同前缀惯例）
- [ ] 无重复方法：两个方法做同一件事（直接删一个或合并）
- [ ] 方法名与字段名/类型名不冲突、不雷同（`player` 参数 vs `Player` 类型）
- [ ] 参数名语义化：不用 `a`/`b`/`tmp`/`data1` 这类无意义命名

## 二、缺陷审查

按重要性分级逐项排查：

### 高危（必须修复）
- [ ] 空引用：`TShock.Players[i]`、`plr.TPlayer`、`plr.Account`、`plr.Group` 访问前判空
- [ ] 数组/索引越界、除零、`null` 集合遍历
- [ ] 死循环/无限重试/无终止条件的递归
- [ ] 资源泄漏：流/文件句柄/定时器/`Task` 未释放或未 Dispose
- [ ] 线程安全：并发写裸 `Dictionary`/`List`（应改 `ConcurrentDictionary` 或加锁）
- [ ] 权限绕过：命令/敏感操作缺权限校验
- [ ] 登录绕过：涉及账号数据的逻辑未检查 `plr.IsLoggedIn`
- [ ] 明文存储/传输敏感数据（密码、Token 等）

### 中危（应修复）
- [ ] 边界条件：空输入、超长输入、0 值、负值、最大值
- [ ] 异常吞噬：`catch` 后既不处理也不记日志
- [ ] 魔法数字：未用常量/注释说明
- [ ] 竞态条件：检查与使用之间状态可能被其他线程改变
- [ ] 热路径性能：循环内重复分配对象、无谓 LINQ、频繁字符串拼接

### 低危（顺手修）
- [ ] 冗余分支（`if` 恒真/恒假）
- [ ] 不可达代码
- [ ] 注释与实现不符（误导性注释）

## 三、多余字段审查

- [ ] 每个字段/属性/常量都被实际引用（用 IDE 未使用提示或全局搜索确认）
- [ ] 无多余配置项：配置里没有用户不会改、改了也没作用的项
- [ ] 无重复存储：两个字段存同一份数据（留一个，另一个用属性转发或删除）
- [ ] 公开属性是否真的需要公开（不必要的公开会暴露内部状态）
- [ ] 无永远为 false / 永远不变的标志位
- [ ] 无残留调试字段（`debugXxx`/`testFlag`/临时计数器）
- [ ] 无多余 `using` 指令、无未使用的 `#region` 空壳

## 四、整体代码质量

- [ ] 类职责单一，每个类 ≤ 400 行，无「上帝类」
- [ ] 无复制粘贴重复代码（相同逻辑已提取为共用方法）
- [ ] 中文 `//` 注释解释「为什么」，且与实现一致
- [ ] 配置/缓存/业务/命令分层清晰
- [ ] 所用 API 与 L1/L3 参考源核对过签名（不靠猜）
- [ ] 事件注册/注销成对（Dispose 里全部注销）
- [ ] 本次改动未夹带无关重构（若夹带了，拆开或回滚）

## 五、需求覆盖核对（对照需求摘要）

逐条核对 Phase 0 记录的需求摘要，确认交付内容与需求一致：

- [ ] 每个功能需求都有对应实现（无遗漏）
- [ ] 每条命令都有注册 + 权限校验
- [ ] 每个权限名与需求一致，默认用户组正确
- [ ] 每个需求中的配置项都存在且可调（无缺失）
- [ ] 边界条件（适用玩家/状态/时机）与需求一致
- [ ] 无需求之外的多余功能（范围蔓延）

核对结果记入审查报告；有遗漏或偏离 → 回到 Phase 4 补齐后再复审。

## 六、审查输出

向用户报告，格式如下：

```
终审代码审查结论：
- 方法名问题：发现 N 个，已修复 N 个
- 缺陷：高危 N 个 / 中危 N 个 / 低危 N 个，已修复 N 个
- 多余字段：清理 N 个（字段/配置项/using/调试残留）
- 需求覆盖：全部实现 / 遗漏 N 项（已补/待补）
- 整体结论：通过 / 需返工
- 遗留说明：<如有>
```

**规则：审查发现的问题必须全部修复后才能进入交付；修复后需重新编译（Phase 6）并重新部署验证（Phase 7），再回到本阶段复审，直到通过。**
